## 📖 项目概述

### 项目简介

**Cc-ETL** 是一款基于 **XXL-Job** 深度改造的企业级可视化定时任务调度平台。平台在保留 XXL-Job 全部功能的基础上，新增了可视化任务编排、DataX 数据同步、多任务串并联执行等高级特性，为企业数据集成、任务调度和自动化运维提供了完整的解决方案。

### 项目定位

- **数据集成平台**：支持多数据源之间的数据同步与转换
- **任务调度中心**：提供强大的任务编排与调度能力
- **可视化运维工具**：通过 Web 端和 PC 端提供友好的操作界面
- **企业级解决方案**：支持高可用、分布式部署，满足企业生产环境需求

### 项目优势

1. **零中间件依赖**：仅需数据库即可部署，降低运维成本
2. **可视化编排**：拖拽式任务编排，降低使用门槛
3. **多端支持**：Web 端 + PC 端，满足不同使用场景
4. **功能丰富**：支持多种任务类型，覆盖常见业务场景
5. **高可用设计**：支持集群部署，保障系统稳定性

## ✨ 核心特性

### 1. 可视化任务编排

#### 1.1 拖拽式编辑
- 支持节点拖拽、连线、编辑等操作

- **串行执行**：任务按顺序依次执行
- **并行执行**：多个任务同时执行，提升效率
- **混合编排**：支持单任务与任务组之间的串并联组合

#### 4.1 执行器路由策略
- **第一个**：固定选择第一个执行器
- **最后一个**：固定选择最后一个执行器
- **轮询**：依次选择执行器
- **随机**：随机选择执行器
- **一致性HASH**：根据任务参数进行一致性哈希路由
- **最不经常使用**：选择调用次数最少的执行器
- **最近最久未使用**：选择最久未调用的执行器
- **故障转移**：自动故障转移
- **忙碌转移**：选择空闲的执行器

#### 4.2 失败处理策略

- **失败忽略**：失败后继续执行后续任务

#### 4.3 阻塞处理策略
- **单机串行**：同一执行器串行执行
- **丢弃后续调度**：丢弃后续调度请求
- **覆盖之前调度**：覆盖之前的调度请求

执行项目根目录下的数据库脚本：

### 2. 后端配置

#### 2.1 Admin 模块配置

编辑 `cc-job/cc-job-admin/src/main/resources/application.yml`：

```yaml
server:
  port: 8989

spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/cc_job_admin?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai
    username: your_username
    password: your_password

xxl:
  job:
    i18n: zh_CN
    accessToken: default_token
    triggerpool:
      fast:
        max: 200
      slow:
        max: 200
    logretentiondays: 30
    logpath: /path/to/logs  # 日志文件路径，必须配置
```

> ⚠️ **重要提示**：
> - `admin.addresses` 端口必须为 `8989`
> - `logpath` 必须配置，建议与 executor 保持一致
> - 执行器端口不能为 `9999`

> 📸 **图片位置 20**: Admin 配置示例
> 
> ![Admin配置](./doc/image/placeholder/admin-config.png)

#### 2.2 Executor 模块配置

编辑 `cc-job/cc-job-executor/src/main/resources/application.yml`：

```yaml
server:
  port: 8400

spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver
    url: jdbc:mysql://localhost:3306/cc_job_admin?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai
    username: your_username
    password: your_password

cc-job:
  job:
    admin:
      addresses: http://127.0.0.1:8989/xxl-job-admin
    executor:
      appname: cc-job-executor
      port: 12000  # 执行器端口，不能为 9999
      logpath: /path/to/logs  # 日志路径
      logretentiondays: 30
    accessToken: default_token
  executor:
    jsonpath: /path/to/datax/json  # DataX JSON 文件临时存放路径
    pypath: /path/to/datax/bin/datax.py  # DataX Python 脚本路径
```

### 2. 最佳实践

#### 2.1 任务设计原则

1. **单一职责**：每个任务只做一件事
2. **幂等性**：任务可以重复执行而不影响结果
3. **异常处理**：合理设置失败重试和超时时间
4. **日志记录**：关键步骤记录日志，便于排查问题

#### 2.2 任务组设计原则

1. **依赖最小化**：减少不必要的任务依赖
2. **并行优化**：能并行的任务尽量并行执行
3. **失败策略**：合理设置失败处理策略
4. **超时设置**：为每个任务组设置合理的超时时间

#### 2.3 性能优化建议

1. **执行器部署**：根据任务量合理部署执行器数量
2. **数据库优化**：对频繁查询的表添加索引
3. **日志清理**：定期清理过期日志，释放存储空间
4. **资源监控**：监控系统资源使用情况，及时扩容

## ❓ 常见问题

### 1. 部署相关问题

#### Q1: Admin 启动失败，提示数据库连接错误？

**A**: 检查以下几点：
1. 数据库是否已启动
2. 数据库连接信息是否正确
3. 数据库用户是否有足够权限
4. 数据库是否已初始化（执行了初始化脚本）

#### Q2: Executor 无法注册到 Admin？

**A**: 检查以下几点：
1. Admin 地址配置是否正确
2. 网络是否连通
3. AccessToken 是否一致
4. Executor 端口是否被占用

> 📸 **图片位置 48**: Executor 注册问题排查
> 
> ![Executor注册问题](./doc/image/placeholder/executor-register-issue.png)

#### Q3: DataX 任务执行失败？

**A**: 检查以下几点：
1. DataX 是否已正确安装
2. `pypath` 配置是否正确（指向 DataX 的 Python 脚本路径）
3. `jsonpath` 目录是否存在且有写权限
4. 数据源连接信息是否正确
5. Reader 和 Writer 的表结构是否匹配
6. 检查执行器日志中的详细错误信息

> 📸 **图片位置 48**: DataX 任务失败排查
> 
> ![DataX任务失败](./doc/image/placeholder/datax-failure.png)

#### Q4: 任务组执行失败，提示拓扑排序错误？

**A**: 检查以下几点：
1. 任务组中是否存在循环依赖
2. 任务节点是否都已正确关联任务
3. 任务依赖关系是否正确配置
4. 检查任务组 JSON 配置是否完整

#### Q5: Web 端无法访问？

**A**: 检查以下几点：
1. Web 前端是否已启动（`pnpm run dev`）
2. 前端端口是否被占用（默认 5173）
3. 后端 API 地址配置是否正确
4. 浏览器控制台是否有错误信息
5. 检查跨域配置是否正确

#### Q6: PC 端无法连接后端？

**A**: 检查以下几点：
1. Admin 服务是否已启动
2. PC 端配置的后端地址是否正确
3. 网络是否连通（可以 ping 测试）
4. 防火墙是否阻止连接
5. AccessToken 是否配置正确

#### Q7: 任务执行超时？

**A**: 检查以下几点：
1. 任务超时时间设置是否合理
2. 任务组超时时间是否足够
3. 执行器资源是否充足
4. 数据库连接是否正常
5. 网络延迟是否过高

#### Q8: 任务日志无法查看？

**A**: 检查以下几点：
1. 日志路径配置是否正确
2. 日志文件是否存在
3. 日志文件权限是否正确
4. 日志保留天数配置是否合理
5. 磁盘空间是否充足

#### Q9: 增量同步数据不准确？

**A**: 检查以下几点：
1. 增量字段选择是否正确（主键或时间字段）
2. 增量值设置是否合理
3. 数据源时区配置是否正确
4. 增量同步逻辑是否符合业务需求
5. 检查同步前后的数据对比

#### Q10: 任务组暂停后无法恢复？

**A**: 检查以下几点：
1. 任务组是否处于正确的暂停状态
2. 执行器是否在线
3. 任务组配置是否完整
4. 查看任务组日志中的错误信息
5. 尝试重新启动任务组

### 2. 配置相关问题

#### Q11: 如何配置多个执行器？

**A**: 
1. 复制 Executor 模块配置
2. 修改每个 Executor 的 `appname` 和 `port`
3. 确保所有 Executor 的 `admin.addresses` 指向同一个 Admin
4. 启动多个 Executor 实例

#### Q12: 如何配置集群部署？

**A**: 
1. Admin 可以部署多个实例，共享同一个数据库
2. Executor 可以部署多个实例，实现负载均衡
3. 使用 Nginx 做负载均衡（可选）
4. 确保所有实例的配置一致

#### Q13: 如何修改日志保留天数？

**A**: 
在 Admin 和 Executor 的配置文件中修改：
```yaml
xxl:
  job:
    logretentiondays: 30  # 修改为需要的天数
```

### 3. 性能相关问题

#### Q14: 任务执行速度慢？

**A**: 优化建议：
1. 增加执行器数量，实现并行执行
2. 优化 SQL 查询，添加索引
3. 调整 DataX 的 channel 数量
4. 检查数据库连接池配置
5. 优化任务依赖关系，减少串行等待

#### Q15: 系统资源占用过高？

**A**: 优化建议：
1. 限制并发任务数量
2. 调整线程池大小
3. 定期清理过期日志
4. 优化数据库查询
5. 监控系统资源使用情况

### 4. 功能使用问题

#### Q16: 如何实现任务失败后发送告警？

**A**: 
1. 在任务配置中启用"失败告警"
2. 配置告警通知方式（邮件/短信/Webhook）
3. 设置告警规则和接收人
4. 任务失败时会自动触发告警

#### Q17: 如何导出任务组配置？

**A**: 
1. Web 端：在任务组管理页面点击"导出"
2. PC 端：右键点击任务组，选择"导出"
3. 导出的文件为 JSON 格式，可以用于备份和迁移

#### Q18: 如何导入任务组配置？

**A**: 
1. Web 端：在任务组管理页面点击"导入"，选择 JSON 文件
2. PC 端：点击"打开"，选择 `.cetl` 文件
3. 导入后检查任务依赖关系是否正确

## 📞 技术支持

### 获取帮助

如果您在使用过程中遇到问题，可以通过以下方式获取帮助：

1. **查看文档**：首先查阅本文档的"常见问题"部分
2. **GitHub Issues**：在项目仓库提交 Issue，描述问题详情
3. **社区论坛**：访问项目社区论坛（建设中）
4. **邮件联系**：发送邮件至项目维护者

### 贡献代码

欢迎贡献代码！请遵循以下步骤：

1. Fork 项目仓库
2. 创建特性分支（`git checkout -b feature/AmazingFeature`）
3. 提交更改（`git commit -m 'Add some AmazingFeature'`）
4. 推送到分支（`git push origin feature/AmazingFeature`）
5. 开启 Pull Request

### 报告问题

报告问题时，请包含以下信息：

- 操作系统版本
- Java 版本
- 项目版本
- 错误日志
- 复现步骤
